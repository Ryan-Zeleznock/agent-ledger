# pipeline
**Job:** Run identity → policy → approval → ledger → upstream → ledger for one call (proxy mode), or stop after the intent record and answer allow/deny/ask (decide-only mode for the hook collector)
**Depends on:** identity, policy (the reviewed registry), approvals, ledger, upstream (all injected through `PipelineDeps`), types
**Flow:** `createPipeline(deps)` returns `{ handle, decide, recordOutcome }`.
- `handle` is the `CallHandler` that `front` runs. For each `IncomingCall` it calls `deps.identity.resolveAgent(credential)` and `startSession(...)`, builds the authenticated `ToolCall` by explicit field projection (never `{ ...incoming }`, so no credential survives), evaluates the registry (own-property, case-sensitive lookups), requests approval if needed, appends the intent record, executes upstream, appends the outcome.
- `decide` does the same up to the intent record and returns a `HookDecision`; the agent runtime executes the tool. An approved risky call becomes `allow` only after the intent record holding the approval has persisted; with `approvals.kind === "hook-ask"` a `require_approval` becomes `ask` and the intent record says `delegated`. `recordOutcome(callId, outcome)` appends the outcome record when PostToolUse (`ok`) or PostToolUseFailure (`error`) reports back.
**Does NOT:** talk to agents directly, hold credentials past the identity step, or read `suggestions.yaml`
**Spec:** docs/spec.md §3, 6, 7
Status: implemented

## Implementation notes (Fable, 2026-09-30, Slice 1b step B)

**ADR-009 / interface pin 1: `argsHmacKey`.** `PipelineDeps.argsHmacKey: Uint8Array` (≥ `ARGS_HMAC_KEY_MIN_BYTES` = 32, else `createPipeline` throws; the key is copied, never held by reference). `projectArgs(args, clearArgFields(registry, server, tool), key)` keeps the reviewed clear fields verbatim and replaces every other top-level field with `hmac-sha256:<hex>` = HMAC-SHA256(key, JCS(value)), JCS from the `canonicalize` package (RFC 8785; `"main"` is hashed as the JSON text `"main"`, an object in canonical key order). Unreviewed tools, the Codex handoff record and `storeArgs: []` rows store no clear field. **The policy is evaluated on the RAW args** (escalation patterns need real values); only the record carries the projection. The ledger then redacts the stored args as before (defence in depth): an HMAC string survives redaction, but a field whose NAME is sensitive (`password`, `token`, …) is replaced by the ledger's key layer with `[REDACTED:key:<word>]` even though it was already hashed. That is safe and stated here; an auditor holding the key can verify any other hashed field by recomputing it. Sources: RFC 2104, RFC 8785 (see `src/hooks/README.md`, 2026-09-30).

**What `decide` does, in order.** malformed call → deny; Slack validation problems → deny; `identity.resolveAgent` (unknown agent → deny, no record: there is no agent to attribute it to) → `startSession` → ToolCall by explicit field projection (`callId, sessionId, agentId, onBehalfOf?, declaredPlan?, server, tool, args, receivedAt`; never a spread) → Codex MCP rules (ADR-006) → `policy.evaluate` → channel resolution → intent append → answer. Every deny that follows a persisted intent record also appends a `blocked` outcome record (best effort). **Every failed intent append is a deny, reads included**: spec §7's "read allowed and buffered" needs a replay buffer that does not exist yet, and an unrecorded read is a gap nothing would replay; until the buffer exists the pipeline fails closed for every class (`test/todo/pipeline.todo.md` keeps the item open).

**`handle` (proxy mode) is implemented:** same steps, then `upstream.execute`, then an outcome record (`ok`, or `error` with `errorClass` = the thrown error's name or `tool-error` for an `isError` result, plus `durationMs`). A deny returns `{ content: [{ type: "text", text: reason }], isError: true }` and never reaches upstream. `hook-ask` in proxy mode is refused at construction; with a `hookAgent`, `handle` throws when called. An outcome append that fails AFTER the tool ran is swallowed (the result is returned; the gap is visible as an intent without an outcome).

**`recordOutcome`** uses the intent record with the same callId (in-process cache first, then a scan of the ledger via `ledger.read`, last match wins) for `call` and `policy`, so the outcome record chains to the intent, or to the `handoff-to-proxy` record for a governed-by-proxy call. An unknown callId is kept as an orphan: `call` fields `unknown`, `policy` `{ verdict: "require_approval", risk: "unreviewed", ruleId: "orphan-outcome:<callId>" }`. The ledger scan is linear per outcome (fine for a laptop ledger; an index is future work).

**Construction-time checks and one pin conflict.** `createPipeline` is synchronous. It throws on: a short key; `hook-ask` without `hookAgent`; in decide-only mode (`hookAgent` set) a missing, non-integer or already-past `AGENT_LEDGER_WATCHDOG_DEADLINE_AT_MS`; with a `slack` channel and a `hookAgent`, a `timeoutMs` that breaks `validateHookTiming` against `AGENT_LEDGER_WATCHDOG_DEADLINE_MS` (a consistent `hookTimeoutS` is derived, since the handler does not know the agent's timeout). `approvals.validateSlackChannel` is async, so it is started at construction and its problems turn the FIRST `decide`/`handle` into a deny. **Conflict to resolve (flagged in the run report):** pin 4 registers the PostToolUse handler WITHOUT the watchdog, so that process has no `AGENT_LEDGER_WATCHDOG_DEADLINE_AT_MS` and this contract-mandated construction check would make `recordOutcome` unreachable there. Options: the post handler sets the variable itself, or the contract moves the check to `decide()` (deny when missing). Implemented as the contract says; not silently diverged.

**Slack itself is not in this slice.** `approvals.requestApproval` / `validateSlackChannel` are still stubs; `test/pipeline.test.ts` mocks the module to pin the pipeline's contract with it (approval before append, allow only after the append, `unavailable` on a rejection or an unbound result, `deadlineAt` passed through).
