# pipeline
**Job:** Run identity → policy → approval → ledger → upstream → ledger for one call (proxy mode), or stop after the intent record and answer allow/deny/ask (decide-only mode for the hook collector)
**Depends on:** identity, policy (the reviewed registry), approvals, ledger, upstream (all injected through `PipelineDeps`), types
**Flow:** `createPipeline(deps)` returns `{ handle, decide, recordOutcome, recordHeartbeat }`.
- `handle` is the `CallHandler` that `front` runs. For each `IncomingCall` it calls `deps.identity.resolveAgent(credential)` and `startSession(...)`, builds the authenticated `ToolCall` by explicit field projection (never `{ ...incoming }`, so no credential survives), evaluates the registry (own-property, case-sensitive lookups), requests approval if needed, appends the intent record, executes upstream, appends the outcome.
- `decide` does the same up to the intent record and returns a `HookDecision`; the agent runtime executes the tool. An approved risky call becomes `allow` only after the intent record holding the approval has persisted; with `approvals.kind === "hook-ask"` a `require_approval` becomes `ask` and the intent record says `delegated`. `recordOutcome(callId, outcome)` appends the outcome record when PostToolUse (`ok`) or PostToolUseFailure (`error`) reports back.
**Does NOT:** talk to agents directly, hold credentials past the identity step, or read `suggestions.yaml`
**Spec:** docs/spec.md §3, 6, 7
Status: implemented

## Implementation notes (Fable, 2026-09-30, Slice 1b step B)

**ADR-009 / interface pin 1: `argsHmacKey`.** `PipelineDeps.argsHmacKey: Uint8Array` (≥ `ARGS_HMAC_KEY_MIN_BYTES` = 32, else `createPipeline` throws; the key is copied, never held by reference). `projectArgs(args, clearArgFields(registry, server, tool), key)` keeps the reviewed clear fields verbatim and replaces every other top-level field with `hmac-sha256:<hex>` = HMAC-SHA256(key, JCS(value)), JCS from the `canonicalize` package (RFC 8785; `"main"` is hashed as the JSON text `"main"`, an object in canonical key order). Unreviewed tools, the Codex handoff record and `storeArgs: []` rows store no clear field. **The policy is evaluated on the RAW args** (escalation patterns need real values); only the record carries the projection. The ledger then redacts the stored args as before (defence in depth) and **a stored digest survives it under any field name** (Astra P2 #6, 2026-09-30): the ledger's key layer recognises a value that is exactly `hmac-sha256:<64 hex>` as already-protected evidence and keeps it even under a sensitive NAME (`password`, `token`, …), so two different passwords never collapse into one placeholder and an auditor holding the key can verify every hashed field; clear fields with sensitive-looking VALUES are still redacted. This is the ADR-009 reading: every non-allowlisted field keeps its digest. **Two calls are kept apart** (Astra P1 #1): `exec` (raw argument snapshot; what `policy.evaluate` judged and what `upstream.execute` receives) and `stored` (the projection; what every record and Slack preview carries). **Under Codex an `mcp__` hook name never consults a registry row's allowlist** (Astra P1 #2): routing comes first and every Codex MCP hook argument is hashed, for not-proxied denials and handoffs alike; only the proxy, seeing raw upstream identity, uses `storeArgs`. Sources: RFC 2104, RFC 8785 (see `src/hooks/README.md`, 2026-09-30).

**What `decide` does, in order.** malformed call → deny; watchdog deadline absent or past (ADR-011, decide-only mode; see below) → deny; Slack validation problems → deny; `identity.resolveAgent` (unknown agent → deny, no record: there is no agent to attribute it to) → `startSession` → ToolCall by explicit field projection (`callId, sessionId, agentId, agentSessionId?, onBehalfOf?, declaredPlan?, server, tool, args, receivedAt`; never a spread) → Codex MCP rules (ADR-006) → `policy.evaluate` → channel resolution → intent append → answer. Every deny that follows a persisted intent record also appends a `blocked` outcome record (best effort). **Every failed intent append is a deny, reads included**: spec §7's "read allowed and buffered" needs a replay buffer that does not exist yet, and an unrecorded read is a gap nothing would replay; until the buffer exists the pipeline fails closed for every class (`test/todo/pipeline.todo.md` keeps the item open).

**`handle` (proxy mode) is implemented:** same steps, then `upstream.execute`, then an outcome record (`ok`, or `error` with `errorClass` = the thrown error's name or `tool-error` for an `isError` result, plus `durationMs`). A deny returns `{ content: [{ type: "text", text: reason }], isError: true }` and never reaches upstream. `hook-ask` in proxy mode is refused at construction; with a `hookAgent`, `handle` throws when called. An outcome append that fails AFTER the tool ran is swallowed (the result is returned; the gap is visible as an intent without an outcome).

**`recordOutcome`** uses the intent record with the same callId (in-process cache first, then a scan of the ledger via `ledger.read`) for `call` and `policy`. A combined ledger can hold TWO intents per callId (the Codex hook's `handoff-to-proxy` record and the proxy's own record), so the hook (`hookAgent` set) prefers the handoff intent and the proxy prefers the non-handoff one, last match within the preference (Astra P2 #5); the hook's outcome therefore chains to its handoff and the proxy's outcome to its own intent. An unknown callId is kept as an orphan: `call` fields `unknown`, `policy` `{ verdict: "require_approval", risk: "unreviewed", ruleId: "orphan-outcome:<callId>" }`. The ledger scan is linear per outcome (fine for a laptop ledger; an index is future work).

**Construction-time checks.** `createPipeline` is synchronous. It throws on: a short key; `hook-ask` without `hookAgent`; nothing else: no watchdog clock is read at construction (ADR-011; the Slack `timeoutMs` versus `AGENT_LEDGER_WATCHDOG_DEADLINE_MS` check lives in `decide()`, see below). `approvals.validateSlackChannel` is async, so it is started at construction and its problems turn the FIRST `decide`/`handle` into a deny.

**Slack itself is not in this slice.** `approvals.requestApproval` / `validateSlackChannel` are still stubs; `test/pipeline.test.ts` mocks the module to pin the pipeline's contract with it (approval before append, allow only after the append, `unavailable` on a rejection or an unbound result, `deadlineAt` passed through).

## Slice 1c (Fable, 2026-10-01; ADR-010 pins 3, 4, 7 and ADR-011)

**ADR-011: the watchdog deadline is checked in `decide()`, not at construction.** `createPipeline` no longer reads `AGENT_LEDGER_WATCHDOG_DEADLINE_AT_MS`. `decide()` reads it on EVERY call, before identity, registry or any append, and answers `deny` with reason `WATCHDOG_DEADLINE_DENY_REASON` (`agent-ledger: watchdog deadline missing or past`, plus which variable and why) when it is absent, non-integer or already past; with a Slack channel it also re-reads `AGENT_LEDGER_WATCHDOG_DEADLINE_MS` and denies when it is absent or `timeoutMs` no longer fits. So the record-only handlers (`post`, `session-start`, `denied`) construct the pipeline with neither variable set and the 1b CLI shim is gone, while a PreToolUse handler started outside the watchdog can only ever produce a deny line (under the watchdog: `handler-deny`, exit 2, with an explicit reason instead of the old `init:exit-1`). `handle` (proxy mode), `recordOutcome` and `recordHeartbeat` never consult either variable. The Slack clock check (`timeoutMs` against `AGENT_LEDGER_WATCHDOG_DEADLINE_MS`, with a consistent `hookTimeoutS` derived because the handler does not know the agent's timeout) is also made only in `decide()`: an inherited duration that is missing or incompatible denies a `pre` (under the watchdog: `handler-deny`, exit 2, with the `validateHookTiming` violation in the reason) and never blocks construction for a record-only handler (Astra 1c P2 #3, 2026-10-03; the earlier construction-time copy of that check is gone). **Public `decide()` is decide-only:** on a proxy-mode instance (no `hookAgent`) it throws, like `handle` does in decide-only mode, because the deadline gate does not apply to the proxy and the public method must not be a deadline-free `allow` (Astra 1c P2 #5); the proxy decides through `handle`.

**`agentSessionId` (pin 3, pin 4).** The ToolCall projection is `callId, sessionId, agentId, agentSessionId?, onBehalfOf?, declaredPlan?, server, tool, args, receivedAt` (still never a spread); `agentSessionId` is copied only when the IncomingCall carries a non-empty string (the hook collector sets it from the event's `session_id`; proxy mode never does). `src/ledger/validate.ts` accepts it in both modes (`projectToolCall`, scalar-bounded), so the lenient append keeps it and the strict read-back returns it; `test/pipeline.test.ts` pins the round trip through the real jsonl ledger with `verify()` ok.

**`recordHeartbeat(hb, credential)` (pin 3, pin 7).** Decide-only mode only. `identity.resolveAgent(credential)` → `startSession` → ONE intent record: `call = { callId: "heartbeat:<uuid>", sessionId, agentId, agentSessionId: hb.agentSessionId, server: BUILTIN_SERVERS[hb.hookAgent], tool: "SessionStart", args: <the heartbeat facts>, receivedAt }`, `policy = { verdict: "allow", risk: "read", ruleId: "heartbeat:session-start", reason: HEARTBEAT_REASON }`, never an outcome. `args` is a validated field-by-field copy of `SessionHeartbeat` stored in the clear (not through `projectArgs`: these are our own observations, not tool arguments; the ledger redactor still runs on it, and the NODE_OPTIONS value is never present, only the boolean). It throws, writing nothing, on an unknown credential, proxy mode, a `hookAgent` that differs from the pipeline's, a malformed heartbeat, or a failed append; the CLI turns a throw into a stderr line and exit 0. **Pin gap:** pin 3 writes `recordHeartbeat(hb: SessionHeartbeat)` yet asks for `identity.resolveAgent(credential)`; `SessionHeartbeat` is stored in the clear and must never carry the credential, so the credential is the second parameter. Flagged in the run report; B never calls this method.

**Auto-mode denials (pin 7).** `recordOutcome(tool_use_id, { status: "blocked", errorClass: "permission-denied:auto-mode" })` is the unchanged `recordOutcome`: it chains to the intent with that callId (the outcome record carries the intent's `agentSessionId`), or becomes an orphan outcome as today.

## Slice 2a (Fable, 2026-10-03; ADR-012 pin 2)

**`approvals: { kind: "none" }` is the proxy's explicit no-channel choice.** `createPipeline` accepts it in proxy mode only; with a `hookAgent` it throws (`decide-only mode uses hook-ask or slack`), so nothing about the hook collector changes this slice. `hook-ask` in proxy mode is still refused. In `handle`, `require_approval` + `none` follows the exact order of the Codex no-channel branch: `approval = { callId, decision: "no-channel", reason: PROXY_NO_CHANNEL_REASON, decidedAt, channel: "none" }` goes INTO the intent record (the final decision is persisted before anything else), then a best-effort `blocked` outcome record, then the agent receives `{ content: [{ type: "text", text: "agent-ledger: denied (<risk>; <ruleId>): " + PROXY_NO_CHANNEL_REASON }], isError: true }`. Upstream is never called; `approvals.requestApproval` is never consulted. Allowed read/write rows are unaffected. A failed intent append is still the `ledger unavailable` deny (spec §7). `handle` logs nothing itself; the server composition root (`src/server/`) logs one line per request. The report already labels `no-channel` as `denied: no channel` and excludes it from "Asks" (`src/report/render.ts`); no report change. The ledger validator's channel enum is B's one-line change to `APPROVAL_CHANNEL_KINDS` (pin 1); until it lands on a branch, a `channel: "none"` record is refused by the real jsonl ledger and the proxy answers `ledger unavailable` instead of the no-channel text, which `test/pipeline.test.ts` and `test/e2e-slice-2a.test.ts` make visible as self-skipping steps rather than hiding.
