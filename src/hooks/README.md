# hooks
**Job:** Turn a Claude Code or Codex hook event (stdin JSON) into an `IncomingCall` (PreToolUse), an `Outcome` (PostToolUse; Claude Code's PostToolUseFailure and auto-mode PermissionDenied) or a `SessionHeartbeat` (SessionStart, ADR-010), turn the pipeline's `HookDecision` back into the exact `hookSpecificOutput` JSON the agent expects, and define the two-process **watchdog** that is the only thing either agent executes for PreToolUse
**Depends on:** types only (the pipeline is wired in by the `hook` command after Gate 2, not by import; the watchdog imports nothing from this package at all)
**Does NOT:** decide anything, execute tools, or read the registry
**Spec:** docs/spec.md §3, 6, 7
Status: implemented

Why it exists: an MCP proxy never sees a coding agent's built-in tools (Claude Code's Bash, Edit, Write, WebFetch; Codex's Bash, apply_patch). Hooks fire for built-in and MCP tools in both agents and can be enforced by an admin (Claude Code managed settings `allowManagedHooksOnly`; Codex `requirements.toml` `allow_managed_hooks_only`). Local mode is therefore hook collector + MCP proxy, for both agents (ADR-005).

**Two agents, one `agent` argument.** `parseHookInput`, `toIncomingCall`, `toOutcome` and `formatPreToolUseOutput` take `agent: "claude-code" | "codex"`. The wire formats share the core (`session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`) and the output block, so one code path with two type sets is simpler than a second module. Verified 2026-09-29: Claude Code at https://code.claude.com/docs/en/hooks; Codex at https://learn.chatgpt.com/docs/hooks plus the generated schemas in openai/codex `codex-rs/hooks/schema/generated`. Fixtures: `test/fixtures/claude-code-*.json` (PreToolUse, PostToolUse, PostToolUseFailure) and `test/fixtures/codex-*.json` (PreToolUse, PostToolUse; Codex has no failure event).

**Codex differences that change behaviour.** `model`, `turn_id`, `permission_mode` required; `transcript_path` nullable; `tool_input` is "any JSON value" (a non-object is refused → deny); file edits always arrive as `apply_patch` (`Edit`/`Write` are matcher aliases only); a failed command still arrives as `PostToolUse`, so the Codex outcome is `ok` = "ran and returned"; and **`permissionDecision: "ask"` is unsupported: Codex marks the hook failed and CONTINUES the call**, so the Codex formatter rewrites `ask` to `deny` with `CODEX_ASK_UNSUPPORTED_REASON`. Under Codex, `require_approval` needs a Slack channel to ever become an allow.

**Codex MCP identity (ADR-006).** Verified 2026-09-29 in openai/codex `codex-rs/core/src/tools/handlers/mcp.rs`: the hook name is `mcp__` + `namespace.trim_end_matches('_')` + `__` + `name.trim_start_matches('_')`, computed after sanitising and collision hashing, so `github_`/`list_repos` and `github`/`_list_repos` both fire as `mcp__github__list_repos`. A Codex hook name is therefore never an MCP identity. Under Codex the pipeline consults the registry only for built-ins; for `mcp__*` it answers `allow` + `kind: "governed-by-proxy"` when the server segment equals `registry.proxy.codex.serverName` (the Agent Ledger proxy, Codex's single configured MCP server, decides and records with raw upstream identity; the hook writes only a small `handoff-to-proxy` intent record, v2.1) and a recorded deny (`CODEX_MCP_NOT_PROXIED_REASON`) for every other server. Residual: a local server named `<serverName>_` produces the same hook names; the closer is Codex's managed `requirements.toml` `mcp_servers` allowlist (name AND identity must match), spec §7/§8.

**Timing (ADR-006).** A Slack answer takes minutes, so the three clocks are configurable and validated at init: `approvalTimeoutMs + APPROVAL_MIN_MARGIN_MS ≤ deadlineMs ≤ hookTimeoutS × 1000 − WATCHDOG_MIN_MARGIN_MS` (`validateHookTiming`; violation → exit 2). Profiles: `DEFAULT_HOOK_TIMING` (25 s / 30 s, no Slack) and `SLACK_HOOK_TIMING` (300 s / 310 s / 320 s). The watchdog passes its deadline to the handler as `AGENT_LEDGER_WATCHDOG_DEADLINE_MS`. Both agents take `timeout` in seconds with a 600 s default and no upper clamp on PreToolUse (Codex: `timeout_sec.unwrap_or(600).max(1)`, only SessionEnd/Interrupt are clamped to 3 s).

**Naming.** Built-in tools map to `builtin:claude-code` or `builtin:codex` (`BUILTIN_SERVERS[agent]`). `mcp__<server>__<tool>` maps to `<server>/<tool>`, server segment verbatim. Neither agent can put a `:` in that segment: Claude Code allows only `[A-Za-z0-9_-]` in MCP server names and rewrites the rest to `_`; Codex allows `:` in a raw server name (`codex mcp add`) but every hook-visible MCP name passes `sanitize_responses_api_tool_name`, which keeps only `[A-Za-z0-9_]`, so `builtin:codex` arrives as `mcp__builtin_codex__<tool>`. A server segment that normalises to `claudecode`, `builtinclaudecode`, `codex` or `builtincodex` is refused outright under either agent (throw → deny). A Claude Code tool event with `mcp_server` provenance but no `mcp__` prefix is refused too.

**Watchdog** (`runWatchdog`, `validateHandlerOutput`; spec §7). Verified for Claude Code: exit 2 blocks PreToolUse whether or not JSON is printed and even an `allow` JSON cannot override it; exit 0 without a decision, exit 1 WITHOUT valid decision JSON (with valid JSON the JSON alone decides, re-read 2026-09-30; we never rely on it), unparseable or schema-failing stdout, a timed-out hook and a hook that can't start all let the call continue. Codex documents exit 2 + stderr as a block and treats unsupported output as a failed hook that continues. So the agent runs a tiny watchdog process (node built-ins only), which spawns the handler, owns stdout exclusively, captures the handler's stdout/stderr into bounded buffers, enforces `deadlineMs` on its own event loop (SIGKILL, no awaiting), validates the handler's payload against the exact schema and size bound, and emits **exit 2 for every deny and every failure path** (crash, non-zero exit, oversized/invalid/extra-key output, deadline, spawn failure, config or init failure) with the reason on stderr and a deny JSON on stdout. Only a validated allow (or, for Claude Code, ask) is exit 0. Residual limits: a missing watchdog binary, a watchdog killed by the OS, or a user-edited hook entry produce no output and both agents continue; mitigation is managed configuration (Claude Code `allowManagedHooksOnly`; Codex `requirements.toml` `allow_managed_hooks_only` + `[features].hooks = true`) plus a `SessionStart` heartbeat the report checks.

## Implementation notes (Fable, 2026-09-30, Slice 1b step B)

**Files.** `contract.ts` holds the collector (`parseHookInput`, `toIncomingCall`, `toOutcome`, `formatPreToolUseOutput`) and re-exports the watchdog surface. `watchdog.ts` holds every watchdog function and constant, and its runtime imports are exactly `node:child_process`, `node:fs`, `node:process` (the one `import type` from `src/types` is erased at compile time; `test/hooks-watchdog.test.ts` scans both the source and the compiled output). `watchdog-main.ts` is the entry point the agents execute (interface pin 3): `node <dist>/hooks/watchdog-main.js --agent <claude-code|codex> --deadline-ms <n> --timeout-s <n> [--max-output-bytes <n>] -- <handler argv...>`. `runWatchdog` resolves a `WatchdogResult`; `emitAndExit` (same file) does the non-blocking, time-bounded writes and `process.exit`, all within ONE `WATCHDOG_WRITE_BUDGET_MS` window, so even a stalled reader on both fds costs about a second, never the deadline.

**Decisions taken while implementing (all fail-closed):**
- **`watchdog:init:exit-<code>` vs `handler-exit:<code>`.** A non-zero handler exit with NO stdout at all is classified `init` (the handler failed before it could produce a decision: registry refused to load, `createPipeline` threw, missing deadline env); a non-zero exit after any stdout is `handler-exit`. No cooperation from the handler is needed (Astra's `hook` command just exits non-zero on any throw, pin 4). Both are exit 2.
- **Cross-agent events.** `parseHookInput` rejects `model`/`turn_id` under `claude-code` and `prompt_id`/`scratchpad_dir`/`mcp_server`/`is_interrupt`/`duration_ms`/`error` under `codex`, and otherwise tolerates unknown fields, so a field either agent adds in a future release does not turn every call into a deny. Claude Code's `tool_input` must be an object at parse time; Codex's is any JSON at parse time and refused by `toIncomingCall` unless it is a plain object.
- **Args copy** is a JSON round trip (the event came from `JSON.parse`, so it is lossless and shares nothing; an own `__proto__` key stays data).
- **`formatPreToolUseOutput` shortens a reason over `MAX_REASON_CHARS`** (the watchdog would otherwise deny a valid allow for its reason length) and never emits a newline inside the line.
- **Duplicate JSON members are a deny** (Astra P2 #7, 2026-09-30): `JSON.parse` keeps the last of two equal member names, so `{"permissionDecision":"deny","permissionDecision":"allow"}` would read as an allow. `parseJsonNoDuplicates` (a bounded recursive-descent JSON parser in `watchdog.ts`; escapes decoded, so `permission\u0044ecision` is the same key; whitespace and order free) refuses the first repeated name in any object → `watchdog:output:extra-key:<key>`, exit 2.
- **Write budget covers slow progress too** (Astra P2 #4): `writeAllSync` checks the elapsed budget before EVERY attempt on a monotonic clock (`performance.now`), so 1 byte per 300 ms is cut off after `WATCHDOG_WRITE_BUDGET_MS`, not only EAGAIN/zero progress.
- **A failed emission still group-kills** (Astra P2 #3): `runWatchdog` registers its one-shot `killGroupOnce` at module level and `emitAndExit` calls it on any write/mode-switch failure after a validated allow, so a descendant left in the handler's group does not survive the exit 2 (one kill attempt per PGID, ever).
- **`validateHandlerOutput(raw, agent)`** applies the hard cap `MAX_MAX_OUTPUT_BYTES`; the configured `maxOutputBytes` is enforced by the watchdog's capture buffer (+1 byte overflow detection) before validation. The multiple-value detector tries at most 64 `}` positions before settling on `not-json` (both deny).
- **`setNonBlocking`** uses the stdio stream's libuv handle (`_handle.setBlocking(false)`; pipes, sockets and TTYs have it). A stream without a handle is a regular file, where a write never waits on a reader. Anything else throws → treated as a write failure → exit 2 (best-effort deny on whichever fd still works).
- **Group kill:** one `process.kill(-pid, "SIGKILL")` per watchdog, on every failure path after a spawn; ESRCH is swallowed; the allow path never signals the group (the group is usually gone and the PGID could already belong to someone else).
- **Test seams live in tests, not here:** `test/helpers/hooks-watchdog-harness.ts` patches `fs.writeSync`, `process.kill` and the stdio handle's `setBlocking` on the shared built-in objects, then imports `watchdog-main.js`; `test/helpers/hooks-handler.ts` is the scripted handler (loop, junk, oversize, grandchild-holding-pipes, group children, `setsid` escapee, real pipeline). No environment variable in the product code changes watchdog behaviour.
- **`setsid()` escape** is asserted as the stated residual (spec §7): the escapee survives the group kill, the deny is still emitted; the test kills the survivor itself.

**Not done in this slice** (kept open in `test/todo/hooks.todo.md`): the Slack end-to-end profile (fake Slack answering at 299 s / 301 s) and the handler's runtime Slack budgeting, which need `approvals` (stubbed until the Slack slice); the 8 s / 20 s stdin-delay timings are exercised at 1 s / 3 s deadline scale.

## Slice 1c additions (Fable, 2026-10-01; ADR-010, pins 1, 2, 7)

**Two new events, both record-only, never under the watchdog.** `HOOK_EVENT_NAMES` is now `PreToolUse, PostToolUse, PostToolUseFailure, SessionStart, PermissionDenied`; `CODEX_HOOK_EVENT_NAMES` is `PreToolUse, PostToolUse, SessionStart`. Sources read **2026-10-01**:
- Claude Code hooks reference, https://code.claude.com/docs/en/hooks. `SessionStart`: "Runs when Claude Code starts a new session or resumes an existing session"; input = common fields + `source` (`startup` | `resume` | `clear` | `compact` | `fork`), optional `model` ("can be omitted, for example after /clear"), `agent_type`, `session_title`, and on resume/fork (v2.1.251+) `seconds_since_last_response`, `context_tokens`, `prompt_cache_likely_expired`, `estimated_cache_write_usd` (tolerated, never stored). `prompt_id` is "Absent until the first user input". **Stdout trap:** Claude Code "adds stdout it treats as plain text to Claude's context", so the `session-start` handler prints NOTHING on stdout (the CLI README says how). "Only `type: "command"` and `type: "mcp_tool"` hooks are supported." `PermissionDenied`: "fires after Claude Code denies a tool call through the permission system. It does not fire when you block a tool with a PreToolUse hook, when a deny rule in the permission system blocks the call, or when you manually deny a permission prompt"; the events table says "When auto mode denies a tool call"; it "receive[s] `tool_name`, `tool_input`, `tool_use_id`, and `reason`"; "Exit code and stderr are ignored because the denial already occurred." So an auto-mode denial is recorded; **a manual denial at the prompt is unobservable** and the report must say so (pin 8, B's half). `permission_mode` values: `default`, `plan`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`; "Not all events receive this field" (the SessionStart example has none).
- Codex hooks, https://learn.chatgpt.com/docs/hooks. `SessionStart` exists; `source` is "`startup`, `resume`, `clear`, or `compact`" and the matcher "is applied to `source`"; common fields `session_id`, `transcript_path` (nullable), `cwd`, `hook_event_name`, `model`; "The events SessionStart, PreToolUse, … also include `permission_mode`"; `turn_id` is turn-scoped and absent. The page's SessionStart example carries no `model`, so the parser treats it as optional on that event **[H: the common-fields table lists `model`; the example omits it]**. Same stdout trap: "Plain text on `stdout` is added as extra developer context." No `PermissionDenied` exists for Codex (its `PermissionRequest` has no `tool_use_id`; not adopted).

**Parser rules.** SessionStart requires `session_id`, `cwd`, `hook_event_name`, `source` and NO tool fields; every other event still requires `tool_name`, `tool_use_id`, `tool_input` (PermissionDenied additionally `reason`, a string). Under `claude-code`, `turn_id` is still a Codex marker on every event, but `model` is a marker on TOOL events only (it is a documented optional Claude Code field on SessionStart). Under `codex`, `model` and `turn_id` are required on tool events only. **Known limit:** a bare Codex SessionStart (`session_id`, string `transcript_path`, `cwd`, `source`, `permission_mode`) is by specification indistinguishable from a Claude Code SessionStart, so the agent label of a heartbeat comes from the handler's `--agent` flag, never from the event; a misconfigured flag mislabels heartbeats, nothing else.

**How the handlers use them (CLI, pin 5).** `hook --event session-start` prints nothing on stdout, exits 0 always and fills `HeartbeatProbe.watchdogCheck` by running THIS module's compiled `watchdog-main.js` once, as its own process group, with a trivial allow-printing handler and judging its output with this module's strict `validateHandlerOutput` (`ok` | `missing` | `failed`, 3 s cap, group-killed on every exit path); `hook --event denied` is silent and exit 0 too. Neither runs under the watchdog. Details and sources in `src/cli/README.md`.

**New functions.** `toIncomingCall` now sets `agentSessionId = session_id` (verbatim; never into `args`). `toHeartbeat(ev, agent, probe)` maps a SessionStart event plus the CLI's `HeartbeatProbe` (`interpreter`, `nodeOptionsSet`, `watchdogCheck`) onto `SessionHeartbeat`: exactly `agentSessionId`, `hookAgent`, `source`, `permissionMode` (only when the event carries one), and the three probe fields; the NODE_OPTIONS value, `transcript_path`, `cwd`, `model`, `session_title` and the cost fields never appear (pinned by `test/hooks-collector.test.ts`). `toOutcome(PermissionDenied, "claude-code")` → `{ status: "blocked", errorClass: PERMISSION_DENIED_ERROR_CLASS }` (`permission-denied:auto-mode`); the `reason` text is display text and is not stored. Fixtures: `test/fixtures/claude-code-sessionstart.json`, `claude-code-permissiondenied.json`, `codex-sessionstart.json` (the docs' example blocks verbatim; pinned by `test/hooks-fixtures.test.ts`). The watchdog (`watchdog.ts`, `watchdog-main.ts`) is unchanged; the two new handlers never run under it.

**Sources checked for this implementation (2026-09-30):** RFC 2104 (HMAC, https://www.rfc-editor.org/rfc/rfc2104: `H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ text))`, 64-byte block for SHA-256; `node:crypto` `createHmac` is used and `test/pipeline.test.ts` checks it against the hand-rolled construction); RFC 8785 (JCS, https://www.rfc-editor.org/rfc/rfc8785, via the `canonicalize` 5.1.0 package the ledger already hashes with); Claude Code hooks reference (https://code.claude.com/docs/en/hooks: PreToolUse stdin JSON, `hookSpecificOutput.permissionDecision` allow|deny|ask, exit 2 blocks regardless of stdout, `timeout` in seconds, `tool_use_id` on PostToolUse/PostToolUseFailure) as pinned by the fixtures on 2026-09-29; Node `child_process` docs (`exit` vs `close`, `detached: true` = new process group and session) and libuv (`uv_pipe_open` puts a pipe fd into O_NONBLOCK; `Pipe#setBlocking` toggles it), observed in the full-pipe test.
